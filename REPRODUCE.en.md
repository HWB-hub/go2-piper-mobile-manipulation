# Reproduction guide

**Reproducibility limits:** Recorded configurations under `runs/` have local absolute paths replaced with relative paths or placeholders and are historical records, not ready-to-run configs. Some historical reward settings differ from the current scripts; compare them before attempting an exact reproduction. The earlier `robust_stage` checkpoint used by `spin_stage` is not included. `requirements.txt` records observed versions, not a standalone installer; set up compatible Isaac Sim and Isaac Lab first.

[简体中文](REPRODUCE.md) | **English**

Going from nothing to the checkpoints in `runs/` takes three pieces: the robot asset, the Isaac Lab extension packages, and the staged training commands. This document gives the actual command for every step, where each artefact lands, and the values used to verify it. The repository ships code, configs, checkpoints and experiment results only; the USD and meshes are generated by scripts from a pinned upstream commit (~37 MB meshes + ~83 MB USD) and are not committed.

Additional observed pins are recorded in `environment-freeze-reference.txt`. Local and URL dependencies are omitted; this is a reference snapshot, not an installable lockfile.

## 2. Robot asset

### 2.1 Which asset

The Go2 + Piper URDF comes from [Sivan666666/roboduet_go2piper](https://github.com/Sivan666666/roboduet_go2piper) at commit `32f3898`, under `resources/robots/go2_piper/`.

| Item | Value |
| --- | --- |
| Bodies | 21 (base + 4 hip + 4 thigh + 4 calf + piper_link1…8) |
| Joints | 20 (12 leg + 6 arm revolute + 2 gripper prismatic) |
| Driven | 18 (`DRIVEN_JOINT_NAMES = [".*_hip_joint", ".*_thigh_joint", ".*_calf_joint", "piper_joint[1-6]"]`) |
| Action order | Grouped by the number of movable joints between the joint and the root: FL_hip, FR_hip, RL_hip, RR_hip, piper_joint1, FL_thigh, FR_thigh, RL_thigh, RR_thigh, piper_joint2, FL_calf, FR_calf, RL_calf, RR_calf, piper_joint3…6 (not the URDF declaration order; read from `env.scene["robot"].joint_names`) |
| Policy observation | 92 dims (includes 2 gait-phase dims plus target velocity/acceleration terms), see `runs/*/effective_config.json` |

The action order is neither the URDF declaration order nor the joint order of the USD text: it is the order Isaac Lab uses when it loads the articulation (the sequence above). With any other asset, confirm the order first — checkpoints loaded into a different order drive the wrong joints. `scripts/build_asset.py check` derives that order and compares it against the reference list.

### 2.2 Build pipeline

```bash
python scripts/build_asset.py fetch      # download 18 files at the pinned commit, verify sha256 each
python scripts/build_asset.py prepare    # rewrite package:// and ../dae/ to absolute paths
<IsaacLab>/env/Scripts/python.exe -u scripts/convert_asset.py --headless   # URDF → USD (needs Isaac Sim; isaaclab.bat -p works too)
python scripts/build_asset.py mount --preset lowered             # mount lowering patch
python scripts/build_asset.py check                              # verify joint order/bodies/mount heights
```

Artefacts:

```
assets/upstream/                                   # upstream URDF + 7 dae + 10 STL (not committed)
assets/go2piper.urdf                               # path-rewritten URDF
assets/asset_report.json                           # link/joint manifest
isaaclab_extension/roboduet_go2piper/data/go2piper.usd/
    ├── config.yaml                                # conversion parameters (traceable)
    └── go2piper/go2piper.usda                     # the file actually loaded
```

The conversion parameters are fixed in `scripts/convert_asset.py`; three of them must not change: `merge_fixed_joints=True` (`piper_mount` has to merge into base, otherwise the robot is not a single articulation), `make_instanceable=False` (instanceable prims are read-only, the contact-sensor API cannot be written), `run_asset_transformer=False` (otherwise bodies end up in a nested hierarchy and `SceneEntityCfg("robot", body_names=".*_calf")` matches nothing). Merging fixed joints also folds the foot bodies into the calves, which is why every foot test uses `.*_calf` rather than `*_foot`.

### 2.3 Two mount geometries

`mount` changes exactly 4 numbers (robot-local frame, metres):

| prim | Meaning | `--preset original` | `--preset lowered` |
| --- | --- | --- | --- |
| `Mesh/base_link` | mount visual mesh | 0.085 | 0.0562 |
| `Mesh/base_link_1` | mount collision mesh | 0.085 | 0.0562 |
| `Xform/piper_link1` | arm root body offset | 0.208 | 0.1722 |
| `physics:localPos0` of `Physics/piper_joint1` | arm root joint anchor | 0.208 | 0.1722 |

Both geometries must be reproducible: `original` is the upstream URDF as-is (0.085 + 0.123) and is used by every stage except the last; `lowered` is the mount sunk onto the dog's back, used to train `runs/user_mount_adapt_v8` and to replay the six videos at the top of the README.

Rebuilding with the Isaac Sim 6.0.1 converter, `check` should report: all 20 joints, an 18-dim action order matching the reference, 21/21 bodies, 21 prims carrying the contact report API, and the four mount values of the chosen preset. The USD file itself has no fixed hash to compare against: every conversion serialises differently (the header `doc` field carries the temporary directory of that conversion, and `Flattened_Prototype` numbering changes). The sha256 of the training `lowered` USD is `71a69636…`, recorded for traceability only.

The contact report API has to be written into the USD by the conversion script; it cannot be left to spawn time. The 21 links of this asset are nested under `base`, and the `activate_contact_sensors` call Isaac Lab makes at spawn stops descending as soon as it meets a prim with `RigidBodyAPI` — so it only tags `base`. Building an environment from an untreated conversion gives `sensor.body_names == ['base']` and every foot-contact and foot-lift term silently dies. `scripts/convert_asset.py` writes `PhysxContactReportAPI` and `physxContactReport:threshold = 0` onto all 21 rigid bodies after conversion, which restores the full 21-entry `body_names`; `check` verifies the count.

Two things not to forget after changing the geometry: `GO2_CALF_GROUND_Z` in `isaaclab_extension/go2_piper/go2_piper_walk_env_cfg.py` is the measured standing height of the calf body origin for this asset (0.2715 m) — re-measure it after swapping assets or moving the mount, otherwise the phase clearance term is systematically off by 2–3 cm; the two gripper prismatic joints (`piper_joint7/8`) take no action and stay fully closed in the locomotion task, only the pickup task swaps in the half-open configuration from `go2_piper_pick_env_cfg.py`.

## 3. Install the extension packages into Isaac Lab

```bash
<IsaacLab>/source/isaaclab_tasks/isaaclab_tasks/manager_based/locomanipulation/
    go2_piper/            ← copy of isaaclab_extension/go2_piper
    roboduet_go2piper/    ← copy of isaaclab_extension/roboduet_go2piper (contains data/go2piper.usd)
```

`robots.py` builds the USD path from `os.path.dirname(__file__)`, so the package can live anywhere, but `data/go2piper.usd` inside it must not be moved. `isaaclab_tasks` scans and registers task packages automatically; no `__init__.py` in the Isaac Lab tree needs editing.

Confirm registration:

```bash
<IsaacLab>/env/Scripts/python.exe -c "import gymnasium as gym, isaaclab_tasks; print([k for k in gym.registry if 'Go2Piper' in k])"
# should contain Isaac-Go2Piper-Walk-v0 / -Play-v0
```

## 4. Checkpoint lineage

The 11 directories under `runs/` form one chain. Each contains `model_final.pt`, `policy_jit.pt`, `invocation.json` (the command line of that run), `effective_config.json` (full environment config) and `export_validation.json` (export check).

| Stage | Start from | pattern | iters | seed | lr | recipe | mount | time | Output |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `spin_stage` | earlier whole-body policy (task version before this repo) | combined | 600 | 91 | 8e-05 | baseline | original | 22 min | chain entry |
| `natural_stage` | `spin_stage` | combined | 800 | 211 | 1e-04 | natural | original | 28 min | phase-shaped gait |
| `natural_refine` | `natural_stage` | combined | 600 | 221 | 6e-05 | natural | original | 42 min | cadence feedforward + impact term |
| `natural_coordination` | `natural_refine` | combined | 400 | 241 | 4e-05 | natural | original | 15 min | low-rate coordination |
| `natural_balance` | `natural_coordination` | combined | 800 | 261 | 6e-05 | natural | original | 33 min | tighter low-speed tracking |
| `stability_v1` | `natural_balance` | combined | 800 | 311 | 4e-05 | stability | original | 29 min | stability recipe start |
| `stability_v8` | `stability_v1` | combined | 1000 | 381 | 2.5e-05 | stability_support | original | 39 min | **general model** |
| `s_curve_v1` | `stability_v8` | serpentine | 650 | 481 | 2.5e-05 | stability_support | original | 24 min | **S-curve model** |
| `walk_run_v1` | `s_curve_v1` | walk_run | 1000 | 581 | 5e-05 | natural | original | 37 min | walk-run level 1 |
| `walk_run_v3` | `walk_run_v1` | walk_run | 1000 | 601 | 4e-05 | natural | original | 36 min | **walk-run model** |
| `user_mount_adapt_v8` | `stability_v8` | combined | 600 | 691 | 2e-05 | stability_support | lowered | 21 min | **mount adaptation** |

Notes:

* `spin_stage` was trained with the task code from before the refactor (that version had no `--gait_recipe` and no `serpentine`/`walk_run` patterns) and cannot be retrained bit-exactly with the current code; it is shipped as the entry checkpoint. The two earlier stages above it (cooperative, smooth-spin) are products of that older version too and are out of scope.
* The four bold entries are the models whose results the README reports. The seven intermediate checkpoints are in the repository as well, so the whole chain can be rerun, or validation can start from any single level (e.g. `stability_v1`).
* Every stage uses `--profile adaptive`, `--num_envs 512`, `--duration 38` (38 s per episode). Times are the measured 2.0–2.8 s/iteration at 512 envs on an RTX 5070 Laptop 8 GB.

## 5. Staged training commands

Template (the 10 stages differ only in parameters):

```bash
<IsaacLab>/env/Scripts/python.exe -u run_adaptive.py --mode train --profile adaptive \
    --pattern <combined|serpentine|walk_run> --num_envs 512 --iterations <N> \
    --seed <S> --learning_rate <LR> --gait_recipe <natural|stability|stability_support> \
    --duration 38 --checkpoint runs/<parent>/model_final.pt --run_name <stage> --headless
```

Either run them one by one from the table, or use the driver (it reads `scripts/stages.json`, one entry per row above):

```bash
python scripts/train_stage.py --list                                  # print the stage table
python scripts/train_stage.py --through stability_v8 --dry-run        # print commands only
python scripts/train_stage.py --through stability_v8 \
    --python <IsaacLab>/env/Scripts/python.exe                        # actually run (existing checkpoints skipped)
```

The three branches, verbatim:

```bash
python run_adaptive.py --mode train --pattern combined --num_envs 512 --iterations 800 \
```


**Branch B: walk-run** (chained after the S-curve stage, two runs)

```bash

    --seed 581 --learning_rate 5e-5 --gait_recipe natural --duration 38 \
    --checkpoint runs/s_curve_v1/model_final.pt --run_name walk_run_v1 --headless

python run_adaptive.py --mode train --pattern walk_run --num_envs 512 --iterations 1000 \
    --seed 601 --learning_rate 4e-5 --gait_recipe natural --duration 38 \
```

**Branch C: mount adaptation** (the asset must be rebuilt with `--preset lowered` first)

```bash
python scripts/build_asset.py mount --preset lowered
python run_adaptive.py --mode train --pattern combined --num_envs 512 --iterations 600 \
    --seed 691 --learning_rate 2e-5 --gait_recipe stability_support --duration 38 \
    --checkpoint runs/stability_v8/model_final.pt --run_name user_mount_adapt_v8 --headless
```

If VRAM is short, `--num_envs 256` still trains, but the batch statistics of the gait terms differ from 512 — that is a different recipe and the result is not comparable with the shipped checkpoints. Run 512 first.

## 6. Verification

Replay (real time, with video, seeds matching the published clips):

```bash
python run_adaptive.py --mode eval --pattern transition --num_envs 1 --seed 1419 \
    --checkpoint runs/user_mount_adapt_v8/model_final.pt --run_name replay_spin --video
python run_adaptive.py --mode eval --pattern serpentine --num_envs 1 --seed 1482 \
    --checkpoint runs/s_curve_v1/model_final.pt --run_name replay_s --video
python run_adaptive.py --mode eval --pattern walk_run --num_envs 1 --seed 1581 \
    --checkpoint runs/walk_run_v3/model_final.pt --run_name replay_run --video
python run_ground_pick.py --run-name replay_pick --seed 1161 --video
```

For batch statistics (128/256 independent scenes) use `--mode eval --num_envs 128` with the matching pattern; the output goes to `results/<run_name>/evaluation.json` and the pass criteria live in the evaluation block of `run_adaptive.py`. Reference data already in the repository:

| Item | Repository data | Criterion |
| --- | --- | --- |
| General model, in-place spin | `results/stability_v8_fresh_spin/evaluation.json` | 128/128 pass, 0 falls |
| General model, spin/travel transitions | `results/stability_v8_fresh_transition/evaluation.json` | 128/128 pass, 0 falls |
| S-curve | `results/s_curve_test/gait_quality.json` | 127/128 pass, yaw-acceleration RMS 1.65 rad/s² |
| Walk-run | `results/walk_run_v3_contact/walk_run_metrics.json` | 127/128 pass, 0.28 → 1.72 → 0.28 m/s |
| Ground pick | `results/ground_pick_stable_*/evaluation.json` | 48/48 across three positions |

Export check (confirms `policy_jit.pt` matches the training policy):

```bash
python validate_export.py runs/stability_v8
```

Replaying `runs/user_mount_adapt_v8` (`--pattern spin --seed 1409`) on the `lowered` asset rebuilt by this pipeline, with no manual edits, reproduces `results/github_user_mount_spin/evaluation.json` item by item: `successful_episodes = 1`, `fall_count = 0`, `spin_rotation_mean_rad = 6.70748`, `mean_error_m = 0.0118312`, and the six `reset_state_sha256` entries plus the four contact duty factors match exactly — the geometry and contact setup the scripts produce are equivalent to what was trained.

Retraining yields the same recipe and seed but not a bit-identical file: CUDA kernel non-determinism shifts results even for the same seed on a different GPU or driver. "Reproduced" is judged on the statistics above and on the videos, not on checkpoint hashes.
